# Design

## Context

Существующие `GET /planner/scene`, `POST /planner/runs`, `GET /planner/runs/{run_id}` и cancel-операция дают основу для внешнего клиента. Scene Context публикует контракт v2 и `state_version`, а `iiwa_llm_plan_executor` принимает свой прежний упрощённый граф. Датасет экспортирует graph-v3 с целями, узлами `skill`/`observe`, тремя статусами и отдельной схемой каталога. После изменения graph-v3 становится единственным принимаемым форматом; прежний граф не поддерживается. ROS-проект не зависит от файловой системы датасета или процесса обучения.

## Goals / Non-Goals

**Goals:**

- Сделать внешний цикл воспроизводимым: получить согласованный контекст → собрать system/user prompt вне ROS → вызвать собственную модель → отправить ответ → наблюдать или отменить запуск.
- Сделать graph-v3 контракт первичным на публичной границе и сопоставлять его с живым ROS-контрактом только серверными правилами.
- Отклонять неподдерживаемые конструкции до любого движения и не доверять заявлению модели о доступности навыков.

**Non-Goals:**

- Загружать Qwen/LoRA, запускать inference, выбирать провайдера или хранить ключи модели.
- Исправлять качество обучающего набора или менять training/eval код в соседнем проекте.
- Делать вывод о безопасности физической ячейки только по валидности graph-v3; автоматическая приемочная проверка проводится в Webots.

## Decisions

1. **Добавить `GET /planner/context` поверх существующих scene/run маршрутов.** Он формирует один пакет из свежего ROS snapshot: `system_prompt`, `scene`, `catalog`, `response_schema` и версии, включая `state_version`. Это сохраняет inference у владельца модели и не требует копирования данных датасета в runtime.
   - Альтернатива: попросить клиента отдельно вызывать `/planner/scene` и загружать schema/prompt локально. Отклонено, так как версии и снимки легко рассинхронизировать и пользователь вынужден поддерживать несколько контрактов.

2. **Graph-v3 проверяется и преобразуется на стороне executor, а не в веб-роутере.** Веб-слой передаёт payload без нормализации. Исполнитель повторно получает свежую сцену, сравнивает её версию с `context_state_version`, проверяет схему и семантику, затем переводит только поддерживаемые узлы в движок. Валидация и фактическое движение остаются рядом с каталогом навыков и механизмом защиты сцены.
   - Альтернатива: преобразовывать graph-v3 в HTTP API. Отклонено: это дублировало бы каталоги и валидатор за пределами ROS executor.

3. **Схема и system prompt имеют версионируемый источник в ROS-проекте.** В runtime не читается абсолютный путь к датасету. Пакет API экспортирует контракт, совместимый с генератором graph-v3; context endpoint выдаёт фактическую scene/catalog адаптацию, произведённую из текущего Scene Context и его серверного каталога.
   - Альтернатива: импортировать модуль или JSON-файл из `/media/.../QwenDatasetRobotControl`. Отклонено: это нестабильно при развертывании на другой машине и связывает runtime с training workspace.

4. **Графы с `blocked` или `clarification_required` остаются данными для оператора/клиента, а не запусками.** Только `ready` может быть передан исполнительному движку; и он всё равно должен пройти валидацию.
   - Альтернатива: создавать завершённый RunRecord для неисполняемых ответов. Отклонено для первой версии: это меняет семантику run status и усложняет совместимость; API возвращает исходный статус и объяснение как отказ приёма.

5. **Graph-v3 — единственный формат API и executor.** Старый внутренний формат удаляется из публичного submit-пути; payload без `schema_version: 3` отклоняется как неподдерживаемый. Клиент получает схему и контракт из `/planner/context`.
   - Альтернатива: сохранять legacy-путь. Отклонено по требованию проекта: старые модели и старый формат использоваться не будут, а два формата увеличивают риск неоднозначного исполнения.

## Risks / Trade-offs

- **Модельный graph-v3 и runtime catalog используют разные понятия и имена объектов** → адаптировать только значения, для которых есть точное соответствие в живой сцене; при потере семантики отклонять весь план и отражать покрытие в Webots сценариях.
- **Снимок может измениться между получением контекста и отправкой** → требовать `context_state_version` при подаче graph-v3 и повторно валидировать состояние непосредственно перед первым движением.
- **Отчёт показывает ошибки статуса и неиспользование доступных навыков LoRA** → решение модели само по себе никогда не авторизует движение; сервер проверяет каждый узел, навык, ID, исходы и цели.
- **Системный prompt может разойтись с моделью/датасетом** → включать версию prompt/schema/catalog в ответ context и принимать только контрактные версии, известные executor.
- **Текущий движок может не иметь эквивалента всем `observe` predicate или goal predicate graph-v3** → это ожидаемый отказ совместимости, не повод упрощённо исполнять или пропускать проверку.
- **Безопасность HTTP API** → сохраняются действующие сетевые границы API; развёртывание доступно только в доверенной сети оператора, пока отдельная задача аутентификации не определит иной контракт.

## Migration Plan

1. Реализовать контракт graph-v3, адаптер каталога/сцены и тесты паритета без изменения запуска модели.
2. Добавить `/planner/context` и перевести submit payload на graph-v3 с обязательным `context_state_version`; удалить обработку старого формата.
3. Проверить end-to-end на Webots: context, внешний mock/фактический ответ graph-v3, принятие или отказ, status, cancel и отсутствие RunRecord/движения при отказе.
4. После успешной Webots проверки обновить основные OpenSpec, обе корневые README и двуязычную страницу MkDocs.
5. Откат: revert изменений API/executor целиком. Промежуточное совместное обслуживание старого и нового форматов не предусматривается. Никакой автоматический физический прогон не входит в откат или CI.
