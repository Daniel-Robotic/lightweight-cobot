# Design

## Context

Сейчас `/iiwa_scene_context/get_scene` возвращает свежий конверт `scene_json` с `state_version`, доступными навыками и правилами действий. `iiwa_llm_plan_executor` принимает graph-v3, проверяет его против свежей сцены и сообщает терминальный статус. Новый пакет добавляет цикл между пользовательской задачей, внешней LLM и этими двумя существующими границами; детали требований приведены в `specs/llm-task-orchestration/spec.md`.

Общий конфиг проекта — `cobot-setting.yaml`. Он содержит обычные настройки, но может попасть в Git, поэтому ключ модели должен задаваться ссылкой на переменную окружения или иным секретным источником, а не реальным значением в отслеживаемом примере.

## Goals / Non-Goals

**Goals:**

- Запускать долгую задачу одним ROS action и публиковать наблюдаемый прогресс.
- Изолировать транспорт LLM от оркестратора интерфейсом адаптера.
- Сохранять исходную цель и журнал шагов в памяти активной сессии.
- Использовать только актуальные серверные сцену и каталог и существующую валидацию graph-v3.

**Non-Goals:**

- Обучать или размещать веса JEV/других моделей в ROS.
- Поддерживать совместимость с любым произвольным API только за счёт `base_url`; провайдер должен реализовывать выбранный формат или получить отдельный адаптер.
- Восстанавливать активные сессии после перезапуска процесса в первой версии.
- Разрешать модели напрямую вызывать произвольные ROS topics, services, actions или параметры.

## Decisions

1. **Новый пакет координатора, исполнитель остаётся отдельной границей безопасности.** Пакет владеет action-сессией, историей, запросами модели и повторным чтением сцены. Для выбранного действия он формирует минимальный одношаговый graph-v3 и передаёт его существующему `iiwa_llm_plan_executor`; ответ принимается только после серверной проверки. Это избегает копирования MoveIt, проверки навыков и правил свежести в новый пакет. Прямая отправка движения из координатора отклонена.

2. **Адаптер провайдера задаётся полями общего конфига.** В `cobot-setting.yaml` добавляется секция task-agent с `enabled`, `api_format`, `base_url`, `api_key`, `model`, `timeout_sec`, `max_steps` и `max_invalid_responses`. Первый адаптер использует HTTP API формата OpenAI Chat Completions с настраиваемым `base_url`; интерфейс допускает дополнительные форматы отдельными адаптерами. Не вводится привязка к имени JEV или SDK одного производителя. API-ключ допускает подстановку `${ENV_VAR}`; пример конфигурации не содержит настоящего секрета. Буквальное значение допустимо для локального непубликуемого конфига, но секрет не передаётся как ROS parameter и не журналируется.

3. **Структурированный ответ модели содержит один выбор.** Координатор передаёт модели исходную задачу, историю предыдущих результатов, свежие `scene_json` и доступные навыки. Ответ ограничивается схемой `action` либо `clarification_required`/`blocked`/`completed`; `action` имеет один навык и его допустимые аргументы. Дополнительные шаги, неизвестные поля и ссылки отклоняются до вызова executor. Модель не задаёт собственные наблюдения и команды ROS.

4. **Каждый шаг — отдельный graph-v3 run.** Координатор переводит допустимое действие в граф с единственным `skill`-узлом и безопасными переходами исходов, использует текущий `state_version` и уникальный `run_id`, затем опрашивает статус существующего запуска. После терминального успеха он получает новый scene snapshot и только тогда делает следующий вызов модели. Так сохраняются текущие правила graph-v3, идемпотентность и единый активный run на робота.

5. **Сессия ограничена жизненным циклом ROS action.** Исходный текст, сообщения, результаты, run_id и текущий шаг находятся в session record до терминального исхода. Активная сессия отменяется через action cancel, что передаёт отмену executor и запрещает следующие запросы модели. После перезапуска координатора восстановление не обещается; постоянное хранилище можно добавить позднее отдельным требованием.

6. **Успех определяет серверное подтверждение.** Ответ модели `completed` является намерением остановиться, а не доказательством. Координатор сообщает успех лишь если результат executor и свежая сцена подтверждают достижение исходной цели; иначе выдаёт `verification_required` или `operator_required`.

## Risks / Trade-offs

- [Совместимый API может иметь особенности конкретного хостинга] → включить `api_format` в конфиг и добавлять адаптеры без изменения ROS-контракта; ошибки отсутствующего формата выявлять при старте.
- [Модель может повторять недопустимый выбор или зациклиться] → ограничить invalid-response budget и число шагов; при исчерпании завершать без следующего движения.
- [Сетевой сбой после принятия действия затрудняет понимание результата] → сначала проверять существующий `run_id` через status, повторные отправки делать идемпотентными и не создавать второе движение.
- [Ключ может утечь из конфигурации или диагностик] → использовать env-подстановку, не передавать ключ через ROS параметры, фильтровать исключения HTTP-клиента и не включать секрет в сессионную историю.
- [Последовательные запросы модели увеличивают время и стоимость] → задавать тайм-аут и максимальное число шагов; публиковать этапы и причину ожидания в feedback.

## Migration Plan

1. Добавить ключи task-agent в общий конфиг с выключенным по умолчанию режимом и безопасным примером `${LLM_API_KEY}`.
2. Собрать пакет отдельно от существующих пакетов; добавить его запуск в bringup только при включённой настройке.
3. Проверить конфигурацию и цикл на unit/contract тестах, затем провести Webots интеграционную проверку полного цикла. Автоматический запуск на физическом роботе не выполнять.
4. Откатить можно удалением запуска и конфигурационной секции; существующие scene context и executor продолжают работать самостоятельно.

## Open Questions

Нет. Выбор конкретного JEV endpoint остаётся конфигурацией `base_url` при соблюдении OpenAI Chat Completions-совместимого формата; несовместимый формат требует дополнительного адаптера.
