# External API

## Purpose

Фиксирует доступные внешним клиентам HTTP и MCP операции для чтения состояния и отправки команд роботу, включая типы данных, проверку ввода и ошибки зависимостей ROS.

## Requirements

### Requirement: Включаемый сервер
При `web.enabled=true` система SHALL запускать FastAPI на настроенных `host` и `port`, предоставлять OpenAPI-описание и монтировать MCP-приложение по `/mcp`.

#### Scenario: Веб-сервер включён
- **WHEN** основной launch загружает `web.enabled=true`
- **THEN** запускается `iiwa_web_server` с путями к конфигурации эндпоинтов и суставных лимитов

### Requirement: Конфигурируемые маршруты
Маршруты из `api_endpoints.yaml` SHALL создавать HTTP обработчики типов `topic`, `service`, `action`, `fk` и `tf` с описанными полями и тайм-аутами.

#### Scenario: Отключённый маршрут
- **WHEN** запись маршрута имеет `enabled=false`
- **THEN** маршрут не появляется в доступном HTTP API

### Requirement: Чтение состояния
`GET /robot/joint_states` SHALL возвращать имена, положения, скорости и усилия из `/joint_states`; `GET /robot/pose` SHALL возвращать TCP относительно `base_link`, XYZ в метрах, кватернион и KUKA ABC в радианах и градусах.

#### Scenario: Нет сообщения суставов
- **WHEN** `/joint_states` не поступает до тайм-аута маршрута
- **THEN** запрос чтения состояния возвращает HTTP 503

### Requirement: Команды движения через HTTP
`POST /robot/move/joints`, `/robot/move/pose` и `/robot/move/named` SHALL передавать проверенные цели в соответствующие ROS action или service и возвращать `success` и `message`.

#### Scenario: Некорректная длина суставов
- **WHEN** тело запроса `/robot/move/joints` содержит не семь углов
- **THEN** запрос получает 422 и ROS action не вызывается

#### Scenario: Нет ROS-сервера
- **WHEN** соответствующий ROS action или service недоступен до тайм-аута
- **THEN** HTTP обработчик возвращает 503

### Requirement: Единицы HTTP-позы
`POST /robot/move/pose` SHALL принимать XYZ в метрах и A/B/C в радианах по соглашению ZYX; `speed` SHALL лежать в `[0.01, 1.0]`.

#### Scenario: Выбор планировщика без учёта регистра
- **WHEN** клиент указывает `planner="PTP"`
- **THEN** маршрут нормализует ключ до `ptp` до отправки action-цели

### Requirement: MCP-представление
MCP-приложение SHALL строиться из тех же FastAPI-маршрутов, которые зарегистрированы для HTTP управления и чтения.

#### Scenario: Запрос каталога инструментов MCP
- **WHEN** MCP-клиент подключается к `/mcp`
- **THEN** операции, выведенные из маршрутов FastAPI, доступны через MCP-приложение


### Requirement: Контекст внешнего планировщика
Внешний planner API SHALL предоставлять единый пакет контекста для клиента модели: системную инструкцию graph-v3, свежую сцену, фактический каталог навыков и JSON Schema ответа с версиями контрактов.

#### Scenario: Контекст готов для модели
- **WHEN** клиент запрашивает `GET /planner/context` при готовой свежей сцене
- **THEN** API возвращает `system_prompt`, `scene`, `catalog`, `response_schema`, `schema_version=3`, `contract_version`, `catalog_version` и `state_version` из одного согласованного снимка

#### Scenario: Сцена не готова или устарела
- **WHEN** клиент запрашивает контекст без готовой сцены либо при истёкшем сроке свежести снимка
- **THEN** API возвращает HTTP 409 с машинно-читаемым кодом причины и не выдаёт снимок как пригодный для планирования

#### Scenario: Контракт не поддерживается исполнителем
- **WHEN** версия схемы или набора навыков сцены не поддерживается путём исполнения
- **THEN** API отвечает HTTP 409 с кодом `unsupported_contract` и не выдаёт контекст, предлагающий отправку несовместимого графа

### Requirement: Передача ответа внешней модели
Planner API SHALL принимать только нетрансформированный JSON-ответ graph-v3 в `POST /planner/runs` и направлять его в серверную валидацию до исполнения. Запрос SHALL содержать `context_state_version` из пакета контекста; старый формат графа SHALL отклоняться.

#### Scenario: Ответ graph-v3 передан на выполнение
- **WHEN** клиент передаёт валидный объект graph-v3 со статусом `ready`, уникальным `run_id` и `context_state_version` из использованного снимка
- **THEN** API передаёт ответ исполнителю без переписывания его полей и возвращает `accepted` только после успешной серверной проверки и принятия запуска

#### Scenario: Модель просит уточнение или блокирует задачу
- **WHEN** клиент передаёт graph-v3 со статусом `clarification_required` или `blocked`
- **THEN** API возвращает HTTP 422 с кодом `not_executable`, исходным статусом и пояснением, не создавая запуск и не инициируя движение

#### Scenario: Граф не соответствует graph-v3
- **WHEN** ответ имеет неподдерживаемую версию, неизвестные поля либо некорректную структуру
- **THEN** API возвращает HTTP 422 с кодом и путём ошибки в графе, не создавая запуск и не вызывая движение

#### Scenario: Передан старый формат графа
- **WHEN** клиент отправляет граф без `schema_version: 3` или со структурой прежнего executor-контракта
- **THEN** API возвращает HTTP 422 с кодом `unsupported_contract` и не создаёт запуск

#### Scenario: Снимок изменился после получения контекста
- **WHEN** `context_state_version` запроса не совпадает с актуальной `state_version` сцены
- **THEN** исполнитель отклоняет граф с `stale_scene`, API отвечает HTTP 409, а новый запуск не регистрируется

### Requirement: Наблюдение запуска модели
Planner API SHALL позволять клиенту получить текущее состояние принятого графа и отменить активный запуск через существующие операции статуса и отмены.

#### Scenario: Получение хода выполнения
- **WHEN** клиент запрашивает `GET /planner/runs/{run_id}` для принятого запуска
- **THEN** ответ содержит состояние запуска и последнюю доступную информацию о текущем узле, результате или причине терминального состояния

#### Scenario: Отмена движения
- **WHEN** клиент отменяет активный `run_id` через `POST /planner/runs/{run_id}/cancel`
- **THEN** API отправляет запрос остановки исполнителю и возвращает `cancel_requested`; состояние захваченного объекта сохраняется согласно контракту исполнителя
